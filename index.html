Starfield Record Types

Every four-letter record type in Starfield's main game file, what it holds, how many there are, and a real example. These are the codes you see in xEdit, Spriggit and conflict reports: GMST, KYWD, NPC_, CELL, QUST and the rest.

Plugin basics

click to hide

Plugins

A plugin is a game data file. It holds no code or art of its own; it's a database that says what exists in the game and how it behaves. Starfield.esm is the base game, about 1.4 GB. Every mod with a plugin adds to that database or changes it.

Play with .esm files only. .esp files are for mod development in the Creation Kit; don't install them in the game you play. Starfield doesn't use .esl files: a "light" or "medium" plugin is an .esm with a flag set inside it.

Records and their codes

Each entry in the database is a record: one weapon, one quest, one game setting, one placed rock. A four-letter code at its start, the signature, says what type it is. WEAP is a weapon, QUST a quest. Short names get an underscore to make four letters, so a person is NPC_.

FormID and editor ID

Every record has a FormID, an 8-digit hex number such as 0000000F (Credits). The game uses it to find the record. The first two digits say which plugin it comes from, by load order position, so a mod's FormIDs can differ between two players' games. Plugins flagged light all share FE and medium ones FD, with more digits to tell them apart.

Most records also have an editor ID, a readable name such as GameHour or MQ101. Modders and the console use it. Some types, such as navmeshes, have none.

Groups (GRUP)

Records of one type are kept together in a group, marked GRUP in the file: all keywords in one, all quests in another. Starfield.esm has 176 top-level groups. Places are nested: a worldspace holds blocks of cells, and each cell holds what's placed in it. That's why REFR, ACHR, PGRE and PHZD are marked in cells below: they have no group of their own.

Overrides, load order and conflicts

A mod changes a game record by including its own copy with the same FormID. That copy is an override, and it replaces the whole record, not just the part the mod meant to change. When two mods override the same record, the one that loads last wins and the other's change is lost.

That is why load order matters and why conflict patches exist: a patch is a plugin loaded after both mods that carries one record with both changes. Mods that add their own new records instead of overriding the game's don't conflict this way.

Where you see these codes

  • xEdit lists each plugin's groups by code and name, e.g. "KYWD - Keyword", and shows conflicts in color. The names on this page are xEdit's.
  • Creation Kit mostly shows the long names ("Keyword", "Non-Player Character") in its Object Window, but the codes appear in errors, logs and filters.
  • Spriggit turns a plugin into text files you can track in git, sorted by record type.
  • Conflict checkers report which records two mods both change by code, FormID and editor ID.

What the numbers say

  • 86% of all records are placed objects (REFR): every rock, crate and light set into a cell.
  • Dialogue is the next biggest: 126,347 responses (INFO) under 68,154 topics (DIAL).
  • 2,077 quests, most of them hidden background quests rather than entries in your log.
  • Planet generation adds its own types: biomes, surface blocks and patterns, planet content trees. See Space & planets.
  • 18 types are marked not sure: little-documented ones where the explanation is a best guess.

Why record types matter

An example: two mods change Sarah Morgan

Say Mod A gives Sarah Morgan a new outfit and Mod B changes her combat AI. In the game she wears her old outfit, and it isn't obvious why.

Sarah's base record is an NPC_ record (Companion_SarahMorgan, 00005983), and her outfit and her AI settings both live in that one record. When two mods edit the same record, the game doesn't merge their changes: the mod lower in the load order wins the whole record. So Mod B's copy of Sarah, made without Mod A's outfit, replaces Mod A's.

  • You can predict it before playing. A conflict checker or xEdit shows "both mods change NPC_ 00005983".
  • The fix is clear. Change the load order to pick the winner, or make a small patch that combines both changes.
  • It's why careful mods avoid editing game records. Where they can, they add their own records and scripts instead.

The record type also tells you what to check in the console:

  • A mod that adds a quest (QUST): check it with sqs <quest>.
  • A mod that changes a game setting (GMST): check it with getgs <setting>.
  • A mod that places objects (REFR): look for leftovers with Starfield Engine Fixes' DumpPointerHandles.

In short, the record type tells you where a mod's change lives, who else might overwrite it, and which console command shows whether it worked.

One thing, several records

The most common case is a single thing that exists as two records: a base record (the template) and a reference (one copy placed in the world).

Sarah Morgan has two records, with different IDs:

  • NPC_ 00005983 (Companion_SarahMorgan): her base record, holding her stats, face, outfit and AI.
  • ACHR 00005986 (SarahMorganREF): the actual Sarah standing in the Lodge.

Mixing them up gives very different results in the console:

  • player.moveto 00005986 takes you to the Sarah.
  • player.placeatme 00005983 creates a second, brand-new Sarah next to you.
  • Changing her outfit means editing the NPC_ record. Checking whether she's alive, or where she is, means looking at the ACHR.

Items work the same way. The Eon pistol is a WEAP base (000476C4), and every Eon lying around in the world is a separate REFR. player.additem needs the base ID. Clicking a pistol on the floor in the console gives you the reference ID instead, which additem won't accept.

Why it matters when testing: when a bug report says "Sarah's outfit is wrong" or "the scope is missing", the record type tells you which record to look at in xEdit or a conflict checker. Otherwise you could end up comparing the wrong one.
